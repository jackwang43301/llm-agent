# 信控调优场景 RAG 落地方法论

- 场景：城市道路交通信号控制（信控）配时优化辅助智能体
- 核心主题：面向信控工程师的 RAG——从评估到优化的全链路闭环
- 关键词：信号配时、相位相序、绿信比、流量还原、查询改写、父子文档、Deep Search、RAFT 微调、闭环迭代

---

## 一、为什么基础 RAG 在信控调优场景会"水土不服"

### 1. 场景定位

信控调优智能体要解决的是这样一类问题：信控工程师面对一个路口，需要判断"当前配时方案哪里有问题、该怎么调、调完预期什么效果"。他的依据分散在四类知识里——国标规范、信号机厂商手册、路口现状数据（渠化、流量、评价指标）、以及历史调优案例。RAG 的目标是把这四类知识串起来，让工程师用一句自然语言就能拿到有依据、可溯源的调优建议。

### 2. RAG 的失败模式在信控场景的具象化

- **内容缺失**：工程师问"这个路口早高峰东进口左转排队多长"，但该路口没有布设卡口、流量还原也未覆盖，知识库里根本没有排队长度数据。此时任何生成都是编的。
- **召回失败**：问"建国路×大望路的早高峰方案"，召回的却是"建国路×东三环"的方案。两个路口名向量化后差异极小，配时参数却完全不同——喂错了，输出的绿信比就是错的。
- **信息提取错误**：召回的文档没错，但把"平峰方案"的周期 120s 当成了"早高峰方案"的周期 160s，同一张配时表里不同时段的参数被张冠李戴。

### 3. 信控领域为什么要求严苛

- **极致的可靠性**：配时参数是要下发到信号机上真实执行的。周期给错 40s、相位相序给错顺序，直接后果是干线协调被打断、路口溢出，极端情况下会出现冲突相位放行的安全事故。答案必须对，且必须能溯源到具体规范条款或具体方案版本。
- **极深的专业性**：绿信比、相位差、周期、饱和度、绿灯间隔时间、公共信号周期、车均延误、停车次数、绿灯通行率——这些术语工程师张口就来，且同一概念有多种叫法（"绿信比"="split"、"相位差"="offset"、"周期"="cycle length"）。系统必须像干了十年的信控工程师一样理解这些行话。
- **复杂的知识形态**：知识不只是文字。有 CAD 导出的路口渠化图、相位相序示意图（图片）、Excel 配时方案表（多级表头、动辄几百行）、信号机厂商手册 PDF（参数表 + 接线图）、交管局下发的规范红头文件、以及工单系统里的历史调优记录。传统 OCR 抽出来的内容基本无法直接用。

### 4. 项目面临的四大挑战

1. **评估体系缺失**：工程师说"这个答案不对"，但不知道是召回错了还是生成错了。case by case 调 prompt 容易"按下葫芦浮起瓢"。
2. **生成精度差**：能说出"延长东进口绿灯"，但给不出具体秒数，或者给出的秒数违反国标下限。
3. **稳定性与性能不足**：多路检索 + Deep Search 后单次响应超过 20s，工程师失去耐心。
4. **多跳推理能力弱**："这个路口左转为什么难、该怎么调"本质是多跳问题——要先查流量、再查当前配时、再查相似路口方案、最后做比较，单次检索答不出来。

针对这些挑战，沉淀出完整的实施**五步法**，构成闭环。

## 二、核心方法论：信控 RAG 效果评估与优化全链路（五步法）

### 第一步：知识资产的盘点与构建（地基）

RAG 的性能上限取决于知识库质量。最容易犯的错误是：以为所有信控资料用一套切分方法就能入库。实际上配时表、渠化图、国标条款、历史工单，四种东西的处理方式完全不同。

**1. 数据资产梳理**

先把客户手里的东西分门别类列清楚：

- **结构化**：流量还原结果表（路口 × 时段 × 流向 × 流量）、评价指标表（车均延误、停车次数、排队长度、绿灯通行率）、信号机在线状态表。
- **半结构化**：Excel 配时方案表（多级表头长表）、路口渠化属性表（进出口道数量、车道功能、是否有公交专用道）。
- **非结构化**：国标与地标规范 PDF（如 GB 14886《道路交通信号灯设置与安装规范》、GB 25280《道路交通信号控制机》）、厂商手册（海信、莱斯、易华录等信号机的参数配置说明）、交管局红头文件。
- **图片类**：路口渠化图、相位相序示意图、干线协调时距图、卡口点位图。
- **混合类**：历史调优工单（文字描述 + 调整前后配时表 + 效果对比图）。

**2. 摒弃"一刀切"，差异化多通路数据流水线**

- **复合型文档（工单、厂商手册）**：先拆解后重构。用文档解析工具把文本、表格、图片分离；文本走标准清洗切片，表格走"数据原子化 + 上下文注入"，图片走多模态抽取。
- **配时方案表（典型长表格）**：先转换后看字符串长度分布。短表（单时段单相位，十几行）直接转自然语言；中等表基于表头切分；长表（全天多时段 × 多相位，几百行）必须集中处理。

**3. 长配时表的标准化数据结构**

配时表的难点在于表头是多级嵌套的：行是"时段方案"，列是"相位 → 绿灯/黄灯/全红"。切片后数字全成了孤儿。解决办法是让大模型把表格转成带**标题树**和**原子化单元**的 JSON。

标题树只做一件事：把行列的层级关系显式表达出来，让任何一个数值都能定位到树上的一条路径。

```json
{
  "table_id": "TIMING-CY0142-2026Q1",
  "table_title": "建国路×大望路 路口全天配时方案表",
  "metadata": {
    "source_doc": "朝阳区2026Q1配时方案汇总.xlsx",
    "sheet": "建国路大望路",
    "page": null,
    "intersection_id": "CY0142",
    "signal_vendor": "海信",
    "control_mode": "多时段定周期",
    "version": "V3",
    "effective_date": "2026-01-15"
  },
  "semantic_summary": "该路口全天划分5个时段方案，早高峰周期160s，采用东西直行先放、南北直行后放的四相位方案，东进口左转设专用相位。",
  "header_tree": {
    "row_dim": {
      "name": "时段方案",
      "children": [
        {"name": "早高峰", "children": [{"name": "07:00-09:00"}]},
        {"name": "平峰",   "children": [{"name": "09:00-16:30"}]},
        {"name": "晚高峰", "children": [{"name": "16:30-19:00"}]},

      ]

    "col_dim": {
      "name": "相位",
      "children": [
        {"name": "相位1 东西直行", "children": [{"name": "绿灯"}, {"name": "黄灯"}, {"name": "全红"}]},
        {"name": "相位2 东西左转", "children": [{"name": "绿灯"}, {"name": "黄灯"}, {"name": "全红"}]},
```

**4. 原子化单元：让每个数值自带完整上下文**

有了标题树，再把每个单元格拆成一条独立可检索的记录，把它在树上的路径一起写进去。这样在几百行的配时表里查一个参数，语义和数值能对上。

```json
{
  "cells": [
    {
      "cell_id": "TIMING-CY0142-2026Q1#c017",
      "value": 42,
      "unit": "秒",
      "row_path": ["时段方案", "早高峰", "07:00-09:00"],
      "col_path": ["相位", "相位1 东西直行", "绿灯"],
      "semantic": "建国路×大望路路口，早高峰时段（07:00-09:00），相位1东西直行的绿灯时长为42秒。",
      "sibling_context": "该时段周期160秒，相位1绿信比0.26；同相位平峰绿灯时长为35秒。",
      "value_type": "numeric",
      "source": {"doc": "朝阳区2026Q1配时方案汇总.xlsx", "sheet": "建国路大望路", "cell_ref": "D7"},
      "confidence": 0.96
    },
    {
      "cell_id": "TIMING-CY0142-2026Q1#c031",
      "value": 28,
      "unit": "秒",
      "row_path": ["时段方案", "早高峰", "07:00-09:00"],
      "col_path": ["相位", "相位2 东西左转", "绿灯"],
      "semantic": "建国路×大望路路口，早高峰时段，相位2东西左转的绿灯时长为28秒。",
      "sibling_context": "该时段周期160秒，东进口左转小时流量约680辆，饱和度0.91，处于过饱和边缘。",
      "value_type": "numeric",
      "source": {"doc": "朝阳区2026Q1配时方案汇总.xlsx", "sheet": "建国路大望路", "cell_ref": "G7"},
      "confidence": 0.96
    }
  ]
}
```

有了 `sibling_context`，大模型才知道"28 秒不是孤立的，它对应的是一个饱和度 0.91 的左转流向"，这正是后面生成调优建议的关键依据。

**风险与兜底：**

- 客户给的配时表格式极不规范（合并单元格混乱、一个 sheet 里塞多个路口、手填备注列），解析策略会出错。做法是给每条原子记录打 `confidence`，低于阈值（如 0.85）的整表转人工审核，不入正式库。
- 实体表达对不上：工程师嘴里的"东进口左转"、"1 号相位"、"东左"指的是同一个东西，但知识库里只存了"相位2 东西左转"。这个问题留给第四步的查询改写解决。

**5. 图片类知识：多模态抽取 + 三元组**

渠化图和相位相序图是信控知识里信息密度最高的部分，传统 OCR 抽出来是一堆散落的箭头和数字。整体设计是用**多模态大模型**抽取，四个模块串联：

文档预处理与分类 → 多模态解析与抽取 → 评估修正 → 规则与 prompt 库

- **为什么必须先分类**：渠化图关心的是"每个进口道有几条车道、车道功能是什么"；相位相序图关心的是"有几个相位、放行顺序、冲突关系"；时距图关心的是"相邻路口的相位差和绿波带宽"。三种图希望抽的东西完全不同，只有先分类才能用针对性 prompt，避免把图例、图框里的无意义小字也抽进来。
- **规则与 prompt 库**：明确哪类图对应哪个 prompt 模板、每个模板产出什么结构、三元组的主谓宾怎么定义，都要给大模型讲清楚。
- **抽取后产出三元组知识体系**，再用一个参数量更大的模型对三元组做二次评估，判断抽取是否合理、有没有违反交通工程常识（比如抽出了"相位1 与 相位3 同时放行且相互冲突"这种不可能的结论）。

渠化图抽取样例：

```
(CY0142 建国路×大望路, 东进口道, 车道数=4)
(CY0142 东进口道, 车道功能, 左转专用×1 + 直行×2 + 直右×1)
(CY0142 东进口道, 展宽段长度, 85米)
(CY0142 北进口道, 公交专用道, 有)
(CY0142, 进口道渠化形式, 展宽渠化)
```

相位相序图抽取样例：

```
(CY0142 早高峰方案, 相位数, 4)
(CY0142 早高峰方案, 相位顺序, 相位1→相位2→相位3→相位4)
(CY0142 相位1, 放行流向, 东直行 + 西直行)
(CY0142 相位2, 放行流向, 东左转 + 西左转)
(CY0142 相位1, 冲突相位, 相位3/相位4)
(CY0142 相位1→相位2, 绿灯间隔时间, 3秒黄灯 + 2秒全红)
```

同一张图，OCR 只能给出"4"、"85"、"3"这样的孤立数字；转成三元组后，大模型能直接回答"东进口有几条左转车道"、"相位 1 和相位 3 能不能同时放行"。

### 第二步：评测基线与目标设定（标尺 / 导航）

没有量化就永远不知道往哪走。设计两套评估：端到端 + 模块化。

**端到端评估（黑盒）**

不关心内部细节，只看输入什么问题、输出什么答案、是否符合信控工程师预期。数据集以 JSON 落地：

```json
{
  "case_id": "E2E-XK-0087",
  "metadata": {
    "question_type": "配时优化建议",
    "scene": "左转排队",
    "turns": "single",
    "difficulty": "hard",
    "hops": 3,
    "intersection_id": "CY0142"
  },
  "raw_query": "建国路大望路早高峰东边左转排得太长了咋整",
  "rewritten_query": "查询建国路×大望路路口（CY0142）早高峰时段（07:00-09:00）东进口左转流向排队长度偏长的原因，并给出信号配时优化建议",
  "expected_answer": "现状问题：东进口左转早高峰小时流量约680辆，当前相位2绿灯28秒，饱和度0.91已接近过饱和，平均排队长度约120米，超过85米展宽段长度，导致排队溢出占用直行车道。优化建议：周期由160秒调整为170秒，相位2绿灯由28秒延长至36秒，相位1东西直行绿灯由42秒压缩至40秒，其余相位不变。预期效果：东进口左转饱和度降至0.78，车均延误下降约18%。约束校验：调整后周期170秒未超过GB建议的180秒上限，各相位绿灯时长均不低于15秒最小绿灯要求。",
  "expected_docs": [
    "TIMING-CY0142-2026Q1#c017",
    "TIMING-CY0142-2026Q1#c031",
    "FLOW-CY0142-2026W09-AMPEAK-EL",
    "KPI-CY0142-2026W09-QUEUE",
    "GB14886-4.3.2-最小绿灯时长"
  ],
  "scoring_dimensions": ["accuracy", "completeness", "hallucination", "param_validity"]
}
```

要点：

- 现场至少 **100 条以上**，覆盖问题类型（指标查询 / 规范查询 / 现状诊断 / 配时优化 / 方案对比）、单轮多轮、路口类型（主干路交叉、次干路、支路、匝道出入口）、时段场景。
- 一定要**冷启动人工标注**。信控答案的对错只有工程师能判，最开始没法用机器生成。
- 标注时必须同时记录 `expected_docs`，否则后面无法评估召回。

**打分机制**

沿用 0/1/2 三分制，但信控场景要加第四个维度：

1. **答案准确性**：参数、原因诊断是否正确。
2. **完整性**：是否覆盖了"现状问题 + 调整内容 + 优化逻辑 + 预期效果"四段结构。信控工程师要的是能直接进审核流程的方案，缺一段就不可用。
3. **幻觉情况**：单独打分。工业场景可以答不出来，但不能一半对一半错——比如把不存在的"相位5"写进方案，整个建议就作废。
4. **参数合法性**（信控特有的硬约束）：这一维度可以**自动化打分**，不需要人。规则明确：周期是否在 40~180s 之间、单相位绿灯是否 ≥ 最小绿灯时长、黄灯是否为 3s、各相位时长加绿灯间隔是否等于周期、是否出现冲突相位同时放行。任何一条违反直接判 0 分，无论其他维度多高。

第 4 个维度是信控 RAG 相比通用 RAG 最值得单独建的东西：它把"专业知识对不对"这个原本要靠人判的问题，变成了一段可以进 CI 的校验代码。

**模块化过程评估（白盒）**

分四块，每块单独建数据集：

1. **问题改写模块**：验证对信控术语、省略上下文、口语表达的理解能力。把"模型应该生成的 query"与"实际生成的 query"做相似度打分。重点看"东边左转"是否被正确改写为"东进口左转流向"、"1 号相位"是否映射到"相位1 东西直行"。
2. **意图识别模块**：工程师的问题分几类——指标查询、规范条款查询、现状诊断、配时优化、相似路口参考、方案效果预估。评估能否分到正确意图上。分错的典型后果是把"配时优化"当成"指标查询"，只返回数据不给方案。
3. **召回重排模块**：用 `expected_docs` 算 Recall@K、MRR、NDCG。信控场景要特别看一个指标：**同路口不同时段方案的混淆率**——召回结果里有多少是"对的路口、错的时段"。
4. **生成模块**：把召回重排结果和标准答案对比，评估生成质量。

**基线与回归**

- 优化前先跑出**明确基线**：当前版本不做任何优化时，全量 case（如 500 条）在端到端四维度和过程评估各模块上的分数分别是多少。
- 然后**量化目标**：例如"配时优化类问题端到端均分从 0.9 提到 1.6，参数合法性通过率从 62% 提到 98%"，而不是抽象的"效果更好"。
- 之后每次改动都跑**全量回归**，不比基线差才能上线。只解决了三个 badcase 却让五十个 case 劣化，是负向优化。
- 要清楚：没有任何优化不付出代价。加了多路检索响应变慢、加了严格阈值召回率下降，一定存在取舍。保证最关注的部分达标、其余基线不下降，系统才能稳步提高。
- 一句话：**没法衡量就没法优化**。

### 第三步：灵活分层的架构设计与搭建（骨架）

- 按传统软件工程的**高内聚、低耦合**做分层，让每个模块随时可独立优化和替换。
- 信控场景的典型分层：查询理解层（术语改写 + 意图识别）→ 路由层（配时库 / 规范库 / 流量指标库 / 案例库）→ 检索层（向量 + 关键词混合 + 父子关联）→ 重排层 → 生成层 → **约束校验层**。
- 最后那个约束校验层是信控特有的：生成完不直接返回，先跑一遍参数合法性规则，不合法就带着错误原因回炉重生成。这比在 prompt 里反复叮嘱"注意周期不能超过 180 秒"可靠得多。
- 分层之后各团队专注自己那块，最后通过端到端评测确保整体有提升。

### 第四步：全链路优化迭代（肌肉）——三大关键武器

通过评估发现问题 → 提出假设 → AB 测试验证 → 循环迭代。按层拆开优化，避免"一把抓"（A 也改 B 也改，最后不知道是谁的功劳）。

**① 意图理解 / 查询改写（源头）**

工程师的问法极其口语化。原始问题：

> "建国路大望路早高峰东边左转排得太长了咋整"

改写后：

> "查询建国路×大望路路口（CY0142）早高峰时段（07:00-09:00）东进口左转流向的排队长度、流量、饱和度与当前相位绿灯时长，分析排队偏长原因并给出信号配时优化建议"

不改写的后果很直接：向量库里"建国路×大望路"和"建国路×东三环"的相似度极高，"东边左转"匹配不到"东进口左转流向"，很容易召回隔壁路口的方案，把别人的绿信比当成这个路口的答案。

具体技术手段：

- **术语改写 / 同义词替换**：建立信控术语定义库。样例：

```json
[
  {"surface": ["绿信比", "split", "绿信比例"], "canonical": "绿信比（有效绿灯时长与周期时长之比）", "type": "指标"},
  {"surface": ["相位差", "offset", "偏移量"], "canonical": "相位差（相邻路口协调相位绿灯起始时刻之差）", "type": "指标"},
  {"surface": ["周期", "cycle", "周期时长"], "canonical": "信号周期时长（各相位时长与绿灯间隔时间之和）", "type": "指标"},
  {"surface": ["东边左转", "东左", "东进口左", "1号左"], "canonical": "东进口左转流向", "type": "流向"},
  {"surface": ["排队", "压车", "排得长", "堵住了"], "canonical": "排队长度（信控评价指标）", "type": "指标"},
  {"surface": ["早高峰", "早峰", "早上高峰"], "canonical": "早高峰时段（默认07:00-09:00，以路口实际方案时段划分为准）", "type": "时段"},
  {"surface": ["感应", "感应控制", "SCATS自适应"], "canonical": "自适应/感应控制方式（区别于定周期控制）", "type": "控制方式"}
]
```

  改写后"东左饱和度多少"变成"东进口左转流向的饱和度是多少"，检索准确率远高于直接搜"东左"。
  - 风险：术语抽取可能误判，分词切得不好会错误替换（比如把路口名里的"东"当成方向）。
  - 备选：对性能要求不高的场景，用"模型方案"——把术语库和改写逻辑作为提示词喂给大模型，让它做改写，牺牲一点延迟换取容错。

- **父子分类（概念层级匹配）**：工程师问"这个路口的可变导向车道该怎么配时"，知识库里没有"可变导向车道"的专门配时方法，但有"进口道左转专用相位设置方法"的通用规范，而可变导向车道本质上是左转/直行车道功能的动态切换。这就是子类概念与父类概念的匹配问题。
  - 把大量同义词和父子关系全写进 prompt，在几万篇文档规模下不可行：写不全，而且塞进大量用不到的信息反而拉低效果。
  - 方案：**引入外部知识库构建领域词义库**，把同义词与概念层级都放进去。查询时先匹配是否需要替换；需要则生成**多版本查询**，原始 query 一定保留再查一次，同时生成若干新 query，做多路检索 → 去重 → 重排 → 融合生成。

```json
{
  "raw_query": "可变导向车道怎么配时",
  "multi_queries": [
    "可变导向车道怎么配时",
    "可变导向车道信号配时方法",
    "进口道左转专用相位设置方法与配时要求",
    "车道功能动态切换场景下的相位相序设计规范"
  ],
  "concept_path": ["车道渠化", "进口道车道功能", "可变导向车道"],
  "retrieval_mode": "multi_route_hybrid",
  "fusion": "rrf_then_rerank"
}
```

  - 风险：大模型可能生成过于宽泛的 query 引入噪音；词义库有维护成本；多路检索比单次慢，需要配合并发和缓存优化。

**② 检索增强**

- **切块矛盾**：切大块上下文丰富但相关性下降；切小块匹配精准但上下文丢失。配时表和规范条款都吃这个亏——单独一条"绿灯 28 秒"精准但没用，整张配时表召回了又淹没重点。
- **父子文档方案**：
  - 检索时只查**子块**保准确，命中后顺着父子关联把**父块**喂给大模型保上下文。
  - 信控场景的父子映射很自然：子块 = 单个原子化配时单元（`#c031`，"早高峰相位2绿灯28秒"），父块 = 该路口该时段的完整方案（周期、全部四个相位、相位相序、绿灯间隔）。工程师问"东左绿灯多少秒"，子块负责命中，父块负责让大模型看到整个周期结构，才敢说"延长 8 秒并从相位1 借 2 秒"。
  - 规范类文档同理：子块 = 具体条款句子，父块 = 该条款所在的完整章节（含适用条件和例外说明）。只召回条款不召回适用条件，是规范类幻觉的主要来源。
  - 构建时还可以：给每个 chunk 让大模型生成一批可能的提问，与用户问题做匹配；对 chunk 做三元组抽取，让关联知识查询也能命中。
  - Dify 等产品已内置该能力，可先用开源版验证效果，明显好于统一切分。

- **Deep Search（多跳问题）**：
  - 信控调优天然是多跳的。"这个路口左转难该怎么调"需要串联 4~5 份知识：流量还原数据、当前配时方案、评价指标、相似路口方案、国标约束。一次检索命中其中一份就交给大模型，必然答不出来。
  - 方法：拆解子问题 → 知识库路由分别检索 → **反思模块**评估现有信息能否回答原问题 → 够则回答，不够则再拆再检索，直到信息充分。本质是**用时间换质量**。
  - 案例（对应上文 E2E-XK-0087）：

```json
{
  "original_query": "建国路大望路早高峰东边左转排得太长了咋整",
  "decomposition": [
    {"step": 1, "sub_query": "CY0142 早高峰东进口左转的流量与饱和度", "route": "流量指标库"},
    {"step": 2, "sub_query": "CY0142 早高峰当前配时方案（周期/各相位绿灯/相位相序）", "route": "配时方案库"},
    {"step": 3, "sub_query": "CY0142 东进口展宽段长度与车道功能", "route": "渠化三元组库"},
    {"step": 4, "sub_query": "与 CY0142 相似且左转饱和度已改善的路口配时方案", "route": "相似路口案例库"},
    {"step": 5, "sub_query": "信号周期上限与最小绿灯时长的规范要求", "route": "规范库"}
  ],
  "reflection": {
    "after_step_3": {"sufficient": false, "reason": "已知问题成因，但缺少可参考的调整幅度依据"},
    "after_step_5": {"sufficient": true, "reason": "成因、可参考方案、约束条件均已具备，可生成方案"}
  },
  "hops": 5,
  "latency_ms": 8600
}
```

  - 第 3 步是容易被忽略的一跳：展宽段只有 85 米而排队 120 米，说明排队已溢出占用直行车道——这个成因只有把渠化三元组也召回才能推出来，否则方案会只盯着绿灯秒数。

**③ 生成防幻觉（RAFT 微调）**

- SFT 教的是"给定 A 问题按这个结构输出 A'"；**RAFT** 训练的是**抗干扰能力**。
- 问题根源：召回不可能完全干净，10 条上下文里往往只有 3~5 条真正相关，大模型难以判断权重，容易参考错的那几条。信控场景最典型的干扰是"对的路口、错的时段"和"相邻路口、相似名称"。
- 做法：构建"**高能窗口 + 干扰窗口**"数据集，必须基于真实业务数据：

```json
{
  "sample_id": "RAFT-XK-0231",
  "question": "建国路×大望路早高峰东进口左转绿灯多少秒，够不够？",
  "golden_chunks": [
    "TIMING-CY0142-2026Q1#c031 早高峰相位2东西左转绿灯28秒",
    "FLOW-CY0142-2026W09-AMPEAK-EL 东进口左转早高峰小时流量680辆，饱和度0.91"
  ],
  "distractor_chunks": [
    "TIMING-CY0142-2026Q1#c063 平峰相位2东西左转绿灯22秒（同路口错时段）",
    "TIMING-CY0155-2026Q1#c031 建国路×东三环早高峰相位2左转绿灯34秒（相邻路口相似名称）",
    "TIMING-CY0142-2025Q4#c031 上一版本方案早高峰左转绿灯25秒（同路口过期版本）",
    "KPI-CY0142-2026W09-QUEUE-WL 西进口左转排队长度45米（同路口错流向）"
  ],
  "answer": "早高峰东进口左转（相位2）绿灯28秒。结合该流向小时流量680辆、饱和度0.91判断，绿灯时长不足，已接近过饱和。",
  "answer_must_cite": ["TIMING-CY0142-2026Q1#c031", "FLOW-CY0142-2026W09-AMPEAK-EL"]
}
```

- 四类干扰项的设计是有意的：错时段、错路口、错版本、错流向，正好对应信控 RAG 最高频的四种召回污染。微调后模型能在 10 条里精准锁定真正该用的 2 条，相当于给召回结果隐式赋权。
- 数据配比经验：golden 与 distractor 大致 1:2~1:3，并保留一部分"完全没有 golden、正确答案是拒答"的样本，训练模型在知识缺失时说"知识库中没有该路口该时段的方案"，而不是硬编一个秒数。

### 第五步：闭环迭代（进化）——badcase 驱动的工程化流程

1. **问题发现与定级**：自动化评测发现的问题 + 信控工程师实际反馈汇总成 badcase。信控场景的定级标准建议直接挂到后果上：P0 是参数违规或冲突相位（会下发到信号机）、P1 是参数错误但合法（会误导工程师）、P2 是完整性不足（工程师需补查）、P3 是表达啰嗦。
2. **方案设计与小范围验证**：针对 badcase 提一个或多个优化设计，设计**小范围可验证**方案。不要上来就全量改，先小批量验证再推进。
3. **敏捷开发与 AB 测试**：与当前基线比较——是否解决 badcase、是否让其他 case 劣化，基于数据决策。
4. **合并上线**：超过基线标准且解决 badcase 才合并推广。这是工程化，不是"想到什么做什么"。

**典型案例一：检索重排问题**

现象：复杂配时查询时召回极差，TOP5 里根本没有目标路口目标时段的方案。

假设方向：

- 数据层面：配时表切片策略是否把多级表头和数值切散了；
- 算法层面：向量模型对路口名、相位编号这类领域实体理解不足（"CY0142" 与 "CY0155" 在向量空间几乎不可分）；
- 通路层面：只用单一向量检索是否已到瓶颈。

验证过程：

- 先引入父子窗口切分 + 原子化单元重做索引，小批量测试；
- 仍不行则换向量模型，甚至用路口名/相位/时段构造正负样本对微调 embedding；
- 再把单一向量通道扩为**混合检索**——路口 ID、时段、相位这类实体走关键词/结构化过滤，语义部分走向量。

现场结论：**混合检索 + 父子窗口切分**组合收益最大。原因不难理解——信控查询里有大量强结构化的硬条件（哪个路口、哪个时段、哪个相位），这些条件用关键词精确过滤远比让向量去"猜"更可靠，向量只需要负责剩下那部分语义模糊的意图。

**典型案例二：生成推理问题**

现象：召回的知识是对的（配时表和流量数据都对），但生成的方案里出现了原文没有的参数——比如凭空出现"相位5"，或者给出"周期 210 秒"这种超出规范上限的值。

可能原因：

- 提示词没把"只能基于给定上下文中存在的相位"这个约束说清楚；
- 上下文片段太多、噪声大，模型没抓住重点；
- 基础模型指令追随能力不足。

解决步骤：先改提示词并加入约束校验层回炉重生成 → 调整重排后 rank 模型的相关性阈值，过滤低质量窗口块不喂给大模型 → 仍不行则收集数据做 SFT，或按上文做 RAFT。

顺序很重要：先做便宜的（prompt、阈值、规则校验），再做贵的（微调）。信控场景的一个额外便利是，参数合法性可以用规则完全兜住，所以约束校验层的性价比排在所有手段第一位。

## 三、非技术因素：决定项目成败的关键

**1. 资源与协作**

- 技术团队必须和信控工程师、交管部门的业务专家高效沟通。很多问题技术团队怎么想都想不明白，但工程师一眼就能看出"这个路口是感应控制，你按定周期去分析当然不对"。
- 要达到好效果，必须有体系化的知识资产。要和客户明确讲清楚：想让智能体给出可用的配时方案，就得有完整准确的配时表、渠化图和历史工单，否则是"无源之水"。很多现场的第一阶段工作其实是陪客户把配时台账梳理规范。

**2. 迭代节奏**

- 把流程**快节奏**跑起来，让客户不断看到进步，而不是等一个月才知道下一步做什么。信控场景尤其适合按"路口批次"迭代：先做通十个重点路口，让工程师用上，再横向铺开。

**3. 商业价值证明**

- 技术价值不由代码决定，由业务证明。技术是手段不是目的。
- 建议加入非技术维度统计：单个路口方案的人工编制耗时、工程师采纳率、方案返工次数、覆盖路口数。
- 用**方案采纳率、单路口调优耗时下降比例、调优后车均延误/停车次数改善幅度**这类指标，把 RAG 的效果量化到客户的人力节约和通行效率提升上，在商业上证明可行，才能持续拿到资源。
- 建立知识库调用**热力图**：工程师问得最多的是哪类问题、哪些路口、哪些规范条款。这能反向指导知识资产沉淀重点——如果 30% 的提问集中在"相似路口方案参考"，那案例库就是最该投入的资产。

## 总结

- 信控调优是对可靠性和专业性要求极高的场景：答案要下发到信号机，错了有真实后果。
- 用五步法从知识构建、评估、架构、优化、迭代做全链路闭环。
- 信控场景相比通用 RAG 的三个特有着力点：**配时表的标题树 + 原子化**（让每个参数自带周期上下文）、**参数合法性作为可自动化的第四评估维度 + 独立约束校验层**（把专业约束从 prompt 里搬到代码里）、**按错时段/错路口/错版本/错流向四类污染构造 RAFT 干扰项**（正对信控召回的高频失效模式）。
- 查询改写、父子文档、Deep Search、RAFT 微调都是实际能落地的工具，但要按"先便宜后贵"的顺序上。
- 强调价值闭环，让信控工程师和交管客户真正认可系统带来的价值。
- 不管技术怎么变，**以终为始、数据驱动、闭环迭代**的核心思想是通用的。
