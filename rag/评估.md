
# 端到端评估数据集规范
数据集格式为 JSONL（每行一个 JSON），每行数据格式如下：

`{
    "id": "test-0", # 数据唯一标识
    "metadata": { # 可以根据需求增加更多的 Key-Value 标签，比如问题维度等
            "category": "配时优化", # 问题分类，具体分类需要根据业务定。比如 配时优化、指标查询、规范查询等。
            "turn": "单轮", # 问题轮次，比如 单轮、多轮等，单轮问题应该占多数。
    },
    "query": "用户问题", # 用户的原始提问
    "history": [{"role": "user", "content": "用户问题"}, {"role": "assistant", "content": "模型回复"}], # 多轮对话历史会话，单轮对话为空数组。
    "re_query":"改写后的query信息"，
    "golden_answer": "人工标注的黄金答复", # 人工标注的黄金答复，可以由大模型生成后人工修订而来
    "related_documents": [ # 可以由多个内容组成，和答案相关的黄金段落
    ["source_file": "xxxx", "content": ""] # source_file： 原始文档名称，content: 文档中的相关段落内容
]
}`

核心难点是标注 related_documents，主要是 content 的内容最好和切分的 Chunk 内容基本相同。所以需要先进行初步的大的 Chunk 切分后，再进行标注。
不需要完全相同，后续测试的时候可以使用编辑距离的方法来比对 Chunk 一致性。或者在原始JSON数据中就给每块内容增加unique id用于标识，此时可以增加 unique_id 字段用来标识。

## **数据集数量和分布性如下：**
* 建议数量：100+（实际过程中可以先建设哪怕10条，再持续建设）
* 冷启动：尽可能的覆盖历史工程师报的case，已有评测数据，尽量人工标注（尤其是query不要自动合成）。
* 多样性：问题分类、问题轮次、问题长度、问题场景、问题领域等多维度进行覆盖。（启动时可以不用，但是要打好metadata标签）

# 端到端评估指标
可以使用当前的评分规则以保持评分的一致性，但是要注意指标换算：

* 答案准确性：1/2/3
* 答案完整性：1/2/3
* 幻觉：1/2/3

## 评分维度说明
**1. 答案准确性评分（1-3分）**

* **3分（优秀）**：答案完全正确，配时参数准确，无误导性信息
* **2分（良好）**：答案基本正确，存在少量不影响核心理解的细节偏差
* **1分（较差）**：答案存在明显错误或误导性信息，可能影响工程师判断

**2. 答案完整性评分（1-3分）**

* **3分（完整）**：全面回答工程师问题，涵盖所有关键信息点
* **2分（基本完整）**：回答了主要问题，但缺少部分重要细节或补充信息
* **1分（不完整）**：仅部分回答工程师问题，遗漏重要信息

**3. 幻觉(1-3分) **
* **3分（没有幻觉）**：答案基于知识库原始知识生成，没有编造部分，即使答案和问题不相关。
* **2分（部分幻觉）**：答案中部分属于幻觉，但不应影响答案整体的准确性。
* **1分（完全幻觉）**：答案完全由大模型的幻觉产生，且答案是错误的。

**4. 参数合法性（0-1分）【信控特有维度】**
* **1分（合法）**：所有参数均符合国标规范要求（周期在40~180s之间、单相位绿灯≥最小绿灯时长、黄灯为3s、各相位时长+绿灯间隔=周期、无冲突相位同时放行）
* **0分（非法）**：存在任意一条参数违反规范要求

## 评分标准
### 准确性
**3分示例：**

* 配时参数解释完全正确，对应的路口名称、周期时长、相位绿灯时间准确无误
* 技术参数、操作步骤描述精确，符合国标规范和厂商手册
* 引用的文档内容与原文一致，无曲解或错误引用

**2分示例：**

* 主要技术信息正确，但在非关键细节上存在轻微偏差
* 解决方案正确但表述不够精确，可能造成理解上的小幅偏差
* 引用内容基本准确，但在格式或细节描述上有小幅差异

**1分示例：**

* 配时参数对应关系错误，给出错误的路口名称或周期时长
* 技术参数明显错误，可能导致设备故障或安全事故
* 引用了错误的文档内容或对文档内容进行了错误解读

### 完整性评分细则
**3分示例：**

* 完整回答现状问题、可能原因、诊断步骤、优化建议、预期效果
* 提供相关的技术背景、注意事项、相关规范链接
* 针对复杂问题给出分步骤的详细指导

**2分示例：**

* 回答了主要问题但缺少部分辅助信息（如注意事项、约束条件）
* 解决方案正确但步骤不够详细，需要工程师自行补充部分信息
* 提供了核心答案但缺少相关的背景说明或扩展信息

**1分示例：**

* 仅回答了问题的一部分，遗漏关键信息
* 没有提供具体的解决步骤或操作指导
* 答案过于简略，无法指导工程师实际操作

### 幻觉评分细则
**3分示例:**

* 配时优化相关的回答由检索到的配时方案和流量数据生成，参数名称、原因、建议均有出处；
* 配时优化回答中没有其他衍生内容，比如不存在的规范条款或路口数据；

**2分示例：**

* 配时优化相关的回答由检索到的配时方案和流量数据生成，参数名称、原因、建议均有出处；
* 配时优化回答中衍生出其他知识，比如优化方案对实际通行的影响以及车辆表现；

**1分示例：**

* 配时优化相关的回答由大模型编造，参数名称、原因、建议等均没有出处；
* 大模型在没有检索内容的前提下，没有进行拒答；

### 参数合法性评分细则（信控特有）
**1分示例：**

* 周期160秒、相位1绿灯42秒、相位2绿灯28秒，周期=42+28+3+2+其他相位时长，符合规范
* 黄灯时间3秒，符合国标要求
* 无冲突相位同时放行，符合交通安全要求

**0分示例：**

* 周期210秒，超过国标上限180秒
* 单相位绿灯12秒，低于最小绿灯时长15秒
* 出现相位1和相位3同时放行且存在冲突
* 黄灯时间5秒，不符合国标3秒要求

### 特殊情况处理
**多轮对话评分：**

* 需要结合对话历史进行评分，考虑上下文连贯性
* 如果当前回答依赖前文信息，应在完整性评分中予以考虑

**无法回答的问题：**

* 如果问题超出信控领域或文档覆盖范围，明确说明无法回答的原因可得2分
* 胡乱回答超出范围的问题应得1分

## 评分流程
1. **理解问题**：仔细阅读工程师问题，明确问题类型和期望答案
2. **对比标准答案**：将模型回答与 golden_truth 进行对比
3. **检查文档引用**：验证引用的 related_documents 是否准确相关
4. **分维度评分**：分别对准确性、完整性和幻觉进行评分，并检查参数合法性
5. **参数合法性自动化检查**：运行脚本检查参数是否符合国标规范要求
6. **记录评分理由**：简要说明评分依据，便于后续分析和改进

问题等级说明(不考虑频率，客户那边视为必现)
为高效管理和解决测试中发现的问题，确保测试资源的合理分配和问题的优先处理，现对测试过程中发现的问题进行分级。具体的分级标准如下：

### 知识类分级标准
**致命：**软件产品出现系统崩溃、核心功能完全丧失等影响产品正常使用，重启服务后依然不能恢复的问题。或者信控调优助手出现大批量回答毫无逻辑、错乱、幻觉、未检索到等问题，判定为部分功能失效。回答出现敏感、有害、违法等信息，采取一票否决权，出现一例即为致命问题。(答案几乎错误、违法违规、参数严重违规)
**严重：**软件功能核心部分丧失，但不影响软件正常使用，或者信控调优助手出现回答毫无逻辑、错乱、幻觉、未检索到，或者出现影响品牌形象(比如带出其他厂商信息)。这类问题影响范围中等，需要优先解决。(答案部分错误、没有违法违规、参数错误但合法)
**一般：**非软件功能核心功能且可绕过的问题，或者信控调优助手回答正确但回答不全、回答冗余、未检索到内容，以及需要在特定条件下才会触发的错误。这类问题影响范围有限，需要在下一个版本中解决。(答案不全、没有违法违规、以及错误)
**建议：**软件核心功能和性能之外的改进建议，或者信控调优助手回答格式及风格瑕疵，没有实际问题，但不是最佳的设计和体验。这类问题影响范围最小，可延迟修复。

### 几个基本原则：

1、软件产品出现系统崩溃、核心功能完全丧失等影响产品正常使用，重启服务后依然不能恢复的问题统一为致命问题；
2、回答出现敏感、有害、违法等信息，采取一票否决权，出现一例即为致命问题；
3、出现致命问题视情况停止当前版本测试，修复后重新启动测试；
4、单条测试用例出现核心动能丧失、系统异常、回答毫无逻辑、乱码、出现影响品牌形象的答案等问题判定为严重问题，出现严重问题视情况继续进行当前版本测试，
