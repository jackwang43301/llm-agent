## 一、父子检索优化技术方案

### 1.1 解决的问题
在 RAG 系统中，检索段落的大小上存在典型的冲突：

1. Query 普遍较短，而检索的段落如果过长，就会导致 Query 和 Passage（段落）的相似度较低。
2. 而如果检索的段落过短（比如之前尝试的细粒度知识方案），会导致缺乏足够的上下文信息。

在之前的实践中，出现了如下问题：

1. 开启细粒度知识后，Query 和细粒度段落的相似度更高，导致召回的短段落导致缺乏上下文信息，回答出现问题。例："相位2绿灯28秒"这个片段匹配度高，但缺少周期、其他相位时长、绿灯间隔等上下文，无法给出完整的优化建议。
2. 语义上比较相似的段落存在于多个文档中，缺乏足够的区分度导致无法精确召回。例："早高峰周期160秒"可能存在于建国路×大望路和建国路×东三环两个路口的方案中。
3. 为解决精确的关键词匹配，额外增加关键词检索逻辑，造成额外的工程复杂度。

### 1.2 父子检索的原理
比较全面阐述父子检索相关方法的资料有：

* [parent_document_retriever.py](https://github.com/langchain-ai/langchain/blob/master/libs/langchain/langchain/retrievers/parent_document_retriever.py)
* [《Dense X Retrieval: What Retrieval Granularity Should We Use?》](https://arxiv.org/pdf/2312.06648)。

简单的说，其中，父区块（Parent-chunk）保持较大的文本单位（如完整配时方案），提供丰富的上下文信息；子区块（Child-chunk）则是较小的文本单位（如单个配时单元），用于精确检索。系统首先通过子区块进行精确检索以确保相关性，然后获取对应的父区块来补充上下文信息，从而在生成响应时既保证准确性又能提供完整的背景信息。你可以通过设置分隔符和最大长度来自定义父子区块的分段方式。

包括两部分：

1. 检索：将文档拆分为较小、集中的信息单元（包括单个配时单元拆分、摘要、问题抽取、三元组抽取等），更加精准的匹配工程师所输入的问题。子分段能快速提供与工程师需求最相关的初步结果。
2. 召回：将包含匹配子分段的更大部分（如完整配时方案、规范章节、渠化图段落）视作父分段并提供给大语言模型（LLM）。父分段能为 LLM 提供完整的背景信息，避免遗漏重要细节（如周期结构、相位相序、绿灯间隔、适用条件），帮助 LLM 输出更贴合知识库内容的回答。

### 1.3 父子检索的实现架构
1. 父 Chunk 存储：采用和之前相同的 Chunk 处理方法，切分出父 Chunk，存储 Chunk 信息到 ES 中（包含大量的冗余信息如原始 XML 等，体积较大）。示例结构如下：

```json
{
    "chunk_id": "xxx", # Chunk 唯一 ID
    "page_content": "xxxx", # Chunk 内容
    "metadata": {}, # 元信息
}
```
2. 子 Chunk 存储和索引：为提升检索速度，建议子 Chunk 单独存储。可以存储到 ES 单独的 Indexes 中或者使用 Qdrant 等向量库存储。示例结构

```json
{
    "sub_chunk_id": "<chunk_id>-xxx", # 子 Chunk ID，建议使用父 Chunk ID 作为开头，方便定位问题
    "content": "xxxx", # 子 Chunk 内容（开启全文索引，兼容之前的全文检索）
    "dense_vector": [], # 稠密 Embedding 向量，用于向量检索（部分类型 keywords, entity_triplet 不需要 dense vector）
    "metadata": {
        "type": "sentence/question/summary/entity_triplet/keywords/custom", # 子 Chunk 类型，包括句子、问题、摘要、实体三元组、关键词、自定义，
        "chunk_id": "xxx", # 父 Chunk ID
        "page_content": "xxxxx", # 父 Chunk 内容（为避免检索两次，可直接缓存父 Chunk 内容到子 Chunk 中）
    }
}
```
> 注：其中的 keywords 类型兼容之前的关键词检索
3. 子 Chunk 生成：需要在文档入库时增加子 Chunk 生成的步骤，包括如下内容
    1. sentence（句子）：【必选】


        * 对文本段落拆句（限制最长句子长度，然后使用 RecursiveCharacterTextSplitter）。
        * 配时表则拼接为单行，比如`<TableRow>路口=建国路×大望路,时段=早高峰,相位2,绿灯=28s</TableRow>`
        * 可以在子 Chunk 句子前增加利于检索的信息（比如路口ID、时段等）

    2. question（问题）：

        * 使用 LLM 对整个父 Chunk 抽取问题，注意尽可能和实际的工程师提问接近。
        * 单个段落抽取 5-10 个左右问题。例："建国路×大望路路口早高峰周期是多少？"

    3. summary（摘要）：

        * 使用 LLM 对整个父 Chunk 进行摘要总结。
        * 也可以进行知识点提取，如果是知识点提取，可以提取 5 个左右知识点。

    4. keywords（关键词）：

        * 兼容之前的关键词逻辑，不变

    5. entity_triplet（实体三元组）：

        * 使用 LLM 抽取段落中的三元组：`(建国路×大望路, 东进口左转, 排队长度120米)`

    6. custom（自定义）：允许人工编辑增加子 Chunk，从而可以快速修正线上检索问题。

4. 父子 Chunk 混合检索召回全过程：
    1. 检索过程（并行）：分路召回 Top 50


        * 全文检索：检索所有子 Chunk 的 content
        * 关键词检索：检索类型为 keywords 的子 Chunk 的 content（兼容之前的关键词检索实现，是使用全文检索来实现的）
        * 向量检索：检索所有子 Chunk 的 dense_vector

    2. 子 Chunk RFF 合并（Top 50）：对多路检索的结果进行 RFF 合并
    3. 父 Chunk 排序去重（Top 20）：对合并后的子 Chunk 转换为父 Chunk 文档列表，排序相同，但是同一父 Chunk 只保留最靠前的。
    4. Rerank 重排（Top 8）：对父 Chunk 进行 Rerank 重排，取 Top 8

        * ⚠️注意⚠️：使用子 Chunk 后，根据历史经验 Rerank 的价值可能不高，此处需要使用检索评估方法评估是否加入 Rerank。
        * 如不需要加入 Rerank，在第三步父 Chunk 选 Top 8 即可。

### 1.4 父子检索的预期收益
1. 解决细粒度知识相似度过高的问题，从而可以引入细粒度知识，预期提升细粒度知识的检索效果。例："相位2绿灯28秒"和"相位2绿灯30秒"相似度高，但属于不同路口，可以通过父 Chunk 的路口 ID 来区分。
2. 可以通过 question、summary 等方式引入辅助检索方法，从而可提升检索效果。且引入后不影响召回。
3. 可以通过 custom 的方式快速修正线上检索 bad case。例：工程师问"建国路×大望路东左排队长度"，可以通过 custom 增加"东进口左转排队长度"这个子 Chunk。
4. 可以在子 Chunk 中增加实体信息或其他元信息，从而针对性的缓解相同语义段落出现在多个文档的问题。例：在子 Chunk 中增加路口 ID、时段等元信息。
